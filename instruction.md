# EpiSODE, standing build brief

You are implementing **EpiSODE** (Epidemiological Signal Observation and Detection Engine), an outbreak cluster detection and assessment system for the department of Medical Epidemiology at Certe, Groningen. It will be published on GitHub under GPL-2.

This brief applies to **every** session. It is deliberately milestone-agnostic: what to build in a given session lives in `MILESTONES.md`.

## 0. Documents

| File | Role |
|---|---|
| `ARCHITECTURE.md` | Canonical specification. Read in full before writing anything |
| `MILESTONES.md` | What to build, milestone by milestone |
| `QUESTIONS.md` | Assumptions awaiting a decision. You create and maintain this |
| `episode-mockup.jsx` | Interface reference: layout, Certe house style, Dutch vocabulary |

The architecture represents several rounds of deliberate design decisions, including ones that look wrong until you know the reasoning. Do not redesign it. If you believe something in it is mistaken or internally inconsistent, say so explicitly and wait, rather than quietly implementing your own version.

## 1. Starting a session

1. Read `ARCHITECTURE.md` in full, every session, not only the first.
2. Read `MILESTONES.md` and `QUESTIONS.md`.
3. Inspect the repository and `git log` to establish what exists.
4. State which milestone you are working on and confirm it before starting. Do not begin the next milestone because the current one looks finished; a milestone is finished when its definition of done is met and the person says so.

Never start a milestone whose predecessor has failing tests.

---

## 2. What you cannot reach

Plan around these rather than working around them.

- **No Diver access.** `certedb::get_diver_data()` cannot be called. Define the ingestion interface and supply a synthetic implementation behind it.
- **SQLite is the production backend**, not a development stand-in. One file, no server, no credentials. Set `journal_mode = WAL` and `busy_timeout`.
- **No patient data.** Everything in this session runs on synthetic records.
- **Certe packages may be unavailable.** `certestats`, `certedb`, `certegis`, `certeplot2` and `certestyle` are internal. Put them in `Suggests`, guard every use with `requireNamespace()`, and provide a documented fallback path so a stranger who clones the repository can run the whole thing. This is not a nicety: the public demo working without Certe infrastructure is what determines whether the project is adopted outside Certe.

Check whether R is installed before assuming you can execute anything. If it is not available, still write the code, and state plainly in your summary that nothing was executed.

    sql/schema.sql

Instance configuration and secrets live **outside** the repository tree, located through an environment variable. `.gitignore` must exclude `*.yaml` instance files, `*.sqlite`, `data/`, and anything resembling a credential. Nothing under version control may ever contain a patient record or a password.

## 4. Conventions

**Naming.** Package `EpiSODE`. Every database table prefixed `episode_`. Function names in `snake_case`, exported functions prefixed where it aids discovery.

**Language.** Code, comments, documentation and commit messages in English. User-facing strings in Dutch by default, supplied through flat JSON under `inst/i18n/` with dotted keys, never hardcoded. Written English uses British spelling.

**Style.** Follow the conventions of the existing Certe packages. If `certestats` or `certedb` sources are available on the machine, read them first and match their idiom. Otherwise: `dplyr` and `dbplyr` for data manipulation, `roxygen2` for documentation, `testthat` third edition for tests.

**Dependencies.** Keep `Imports` lean: `DBI`, `dbplyr`, `dplyr`, `yaml`, `rlang`. `RMariaDB` and `RSQLite` as backends. Everything Certe-internal in `Suggests`.

**Prose style, for anything you write for a human to read.** No em dashes, use commas instead. Concise, no filler.

## 5. Hard rules

These are decided. Do not reopen them.

1. **No LLM at runtime.** The Duiding text is generated from a fragment library: each fragment is an id, a condition function over the cluster object, a narrative slot, and a template with placeholders. Deterministic, testable, translatable. Section 6 of this brief covers what to build now.
2. **No detection settings in the application**, and **no configuration in the repository**. These are two separate rules and both are absolute.

   Thresholds, baselines, MEM configuration and eligibility gates live in the instance configuration read by the cron, located through the environment variable `EPISODE_CONFIG`. The repository is software that anyone may clone; the configuration is operational data belonging to whoever runs it. `inst/config/default.yaml` ships documented defaults, which is software. An instance's actual parameters are not, and must never be committed, referenced by path, or assumed to sit inside the package.

   Reproducibility comes from the database, not from version control: every run writes `config_hash` and `config_snapshot` to `episode_detection_run`, so any result is explainable from the database alone.
3. **State is derived, never authored.** Cluster state follows from classification, the case-free clock and whether the data changed. Implement the derivation as a pure function with its own tests.
4. **Closure is an act, not a classification.** Only Artefact and Normale variatie close themselves. Everything else stays open until a person closes it.
5. **One isolate per patient per episode**, using episode lengths from `episode_pathogen_config`, applied at ingestion.
6. **Levels ascend with aggregation.** L1 Afdeling through L5 Regio. The child in a suppression rule is the lower number. Do not renumber.
7. **The cron owns the facts, the app owns the judgements.** Section 5.0 of the architecture lists which process writes which table. The two never write the same table. **The app only ever inserts**, never updates and never deletes, which is why there is no locking anywhere in this system. Do not add any.
8. **Sample date is the anchor**, and it silently falls back to receipt date upstream, so the reporting delay is measurable only from observed accrual. Build the reporting triangle accordingly.

## 6. Testing, every milestone

- `testthat` third edition. Every exported function has tests.
- Anything with few inputs and invisible failure modes gets exhaustive tests rather than sampled ones. The state derivation function is the clearest example: wrong output there is undetectable until it matters.
- Anything with combinatorial behaviour gets property-based tests. Reconciliation is the clearest example, and `MILESTONES.md` lists the properties it must satisfy.
- Golden-file tests around the `certestats` wrappers, so an upstream default change surfaces as a failing test rather than as a year of artefactual clusters.
- Never weaken a test to make it pass. If a test is wrong, say why, and change it deliberately.

## 8. When to stop and ask

Create `QUESTIONS.md` in the repository root. Whenever you would otherwise guess, write the question there with the assumption you provisionally adopted, and carry on. Likely candidates: exact Diver column names, whether ward patient-days exist, provincial population sources, and the SO-ZI/AMR notification fields.

Do not invent Diver column names or Certe-specific identifiers and present them as if known. Mark every such placeholder clearly.

---

## 9. Ending a session

Every session ends with:

- `R CMD check` passing without errors or warnings, notes acknowledged
- All tests passing
- Work committed with meaningful messages
- `QUESTIONS.md` updated
- A short written summary: what was built, what was deferred, and **anything in the architecture that appeared wrong while implementing it**

That last point matters. Implementation reveals design faults that design review does not, and the architecture is expected to change once real code exists. Report those findings rather than working around them silently.

If you run out of time mid-milestone, stop at a point where tests pass, even if that means delivering less. A half-written algorithm with passing tests around the finished part is recoverable; a fully written one with no tests is not.
